# SOC Threat Hunting Lab - Atomic Red Team Detection and Splunk Dashboarding

## Overview

After successfully setting up Sysmon telemetry, PowerShell logging, and Splunk ingestion in the previous phase of the lab, I wanted to move beyond simple PowerShell payload execution and simulate actual MITRE ATT&CK techniques.

To do this, I used Atomic Red Team on the Windows VM to safely emulate attacker behavior and then used Splunk to investigate the generated telemetry.

The goal of this phase was to:
- simulate real MITRE ATT&CK techniques
- generate suspicious Windows activity
- investigate the activity using Splunk
- build a SOC-style dashboard for threat hunting and visibility

This phase focused on three MITRE ATT&CK techniques:
- T1003 - OS Credential Dumping
- T1053.005 - Scheduled Task Persistence
- T1047 - Windows Management Instrumentation (WMI)

## Why Atomic Red Team

Atomic Red Team provides small, controlled attack simulations mapped directly to MITRE ATT&CK techniques. Instead of using real malware, Atomic Red Team safely emulates attacker behavior so defenders can:
- test detections
- validate telemetry
- improve SIEM visibility
- practice SOC investigations

This made it perfect for building a realistic SOC threat hunting workflow in the lab.

## Installing Atomic Red Team

To install Atomic Red Team, I used the official Red Canary PowerShell installation command:

```powershell
IEX (IWR 'https://raw.githubusercontent.com/redcanaryco/invoke-atomicredteam/master/install-atomicredteam.ps1' -UseBasicParsing);
Install-AtomicRedTeam -getAtomics
```

This downloaded:
- Invoke-AtomicRedTeam
- Atomic test definitions
- MITRE ATT&CK technique simulations

The installation completed successfully and the PowerShell output confirmed that Atomic Red Team was ready to use.

![Atomic Red Team Installed](atomicinstalled.png)

## Troubleshooting Atomic Paths

One issue I ran into during setup was that Atomic Red Team could not automatically find the Atomics folder. Some techniques initially failed because the PowerShell module was searching for the wrong directory.

To fix this, I manually set the path variable to the Atomics folder:

```powershell
$PathToAtomicsFolder = "C:\AtomicRedTeam\atomics\atomics"
```

After setting the path manually, the Atomic tests executed correctly.

This was actually helpful because it gave me a better understanding of how Atomic Red Team references technique definitions and YAML files internally.

## Simulating T1003 - OS Credential Dumping

The first technique I simulated was T1003, which maps to OS Credential Dumping in the MITRE ATT&CK framework.

Credential dumping is commonly used by attackers to extract credentials from memory or Windows authentication processes such as LSASS.

I executed the Atomic test using:

```powershell
Invoke-AtomicTest T1003 -PathToAtomicsFolder $PathToAtomicsFolder
```

## Simulating T1053.005 - Scheduled Task Persistence

Next, I simulated T1053.005, which involves creating scheduled tasks for persistence or execution.

Attackers commonly abuse scheduled tasks to:
- maintain persistence
- trigger payloads automatically
- execute malicious commands later

I executed the Atomic test using:

## Building the SOC Dashboard

To make the telemetry easier to analyze, I created a SOC-style Splunk dashboard that visualized suspicious activity generated by the Atomic tests.

The dashboard included:
- attack activity timelines
- suspicious activity frequency
- telemetry source distribution

The purpose of the dashboard was to help quickly identify suspicious behavior without manually searching through every event.

This mimics how SOC analysts use SIEM dashboards in real environments to:
- speed up investigations
- identify anomalies faster
- monitor attacker activity
- visualize detection coverage

![Final Splunk Dashboard](splunkdashboardfinal.png)

## Dashboard SPL Queries

The Splunk dashboard included multiple panels to help visualize suspicious activity generated during the Atomic Red Team simulations. Instead of manually searching through raw events, the dashboard made it easier to quickly identify attack activity, telemetry spikes, and suspicious Windows behavior.

The dashboard included the following SPL queries:

### Threat Activity Timeline

This panel visualized suspicious activity over time using a line chart.

```spl
(lsass OR schtasks OR wmic OR powershell)
| timechart span=30m count
```

### Telemetry Source Distribution

This panel grouped suspicious telemetry by source to help identify where the logs were being generated from.

```spl
(lsass OR schtasks OR wmic OR powershell OR calc.exe)
| stats count by source
```

### Suspicious Activity Frequency

This panel displayed the overall count of suspicious attack-related activity generated during the simulations.

```spl
(lsass OR schtasks OR mimikatz OR procdump OR wmic OR WmiPrvSE.exe)
| stats count
```
